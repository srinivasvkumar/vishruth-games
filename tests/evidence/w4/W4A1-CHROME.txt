==================== ROOT CAUSE (diagnosis only — no fix applied) ====================
The spec drives window.game.getUISystem().setScore(n) and asserts the DOM
holds the driven value on the next read. But GameScene.onUpdate()
(src/scenes/GameScene.ts:225-230) pushes setScore(scoreManager.getScore())
UNCONDITIONALLY every frame:

    if (this.player) {
      const state = this.player.getState();
      this.game.getUISystem().setScore(this.scoreManager.getScore());
      ...
    }

In a fresh run the true score is 0, so every rAF tick overwrites the driven
value with "SCORE: 0". Whether the spec's read lands before or after the
next frame tick is a pure race:
  - Chromium (SwiftShader): measured avg frame interval 16.87 ms -> the
    rAF push almost always lands before the spec's ~50-250ms read
    round-trip -> DETERMINISTIC failure.
  - Firefox (GPU): measured avg frame interval 7.05 ms -> the race is
    narrower and the spec's read frequently lands in the gap right after
    the drive -> PASSES most of the time.

Probe evidence (identical drives, 50ms polling):
  Chrome: drive(42) -> 42 | 0 | 0 | 0 | 0 ...   (revert on frame 2)
  Chrome: drive(999) -> 999 | 0 | 0 | 0 | 0 ...  (revert on frame 2)
  Firefox in-page rAF poll after drive(999): 0 x40 frames (revert observed)
  Firefox spec-pattern replay (5 fresh runs): read42=42/0/42/0/0
                                              read999=999/999/999/999/0
  => Firefox is FLAKY on the same spec too (3/5 runs read SCORE: 0);
     the official W4-A.1 Firefox run happened to pass all reads.

This is a spec/production-contract mismatch, NOT a product rendering bug:
  - The real score pipeline (state -> event -> ScoreManager -> HUD push)
    works: CP3 S1 and S4 are green (PLAYER_SCORE(100) -> +100 in state AND
    HUD reflected next frame).
  - The driven setScore() is correctly applied to the DOM — it is just
    overwritten by the legitimate per-frame state->HUD sync ~1 frame later.
  - CP3 S2 was green in W3-B.7-v2 (evidence W3B7V2-CHROME.txt) — the
    per-frame push in GameScene.onUpdate (lines 223-230, "W3A.2: HUD is
    owned by UISystem") has been in place since W3A; the spec passed
    before at the mercy of frame-timing. The two W3-C commits touching
    GameScene.ts (3c758fc perf(input), fd69fa8 settings UI) do not add the
    push; the pre-existing push + slower SwiftShader frame cadence on this
    box is what made the race deterministic.

Classification: MAJOR (spec defect — W4 gate #1 evidence is contaminated:
CP3 "DOM updates when setScore is driven" cannot be trusted in either
browser until the spec is fixed). Product score functionality itself is
healthy per S1/S4. No product code change required by this test alone.

Suggested fix directions (for orchestrator/game-dev, NOT applied here):
  a) Spec-side: assert the DOM read inside the same evaluate() call that
     drives setScore (same JS task, no frame tick in between), OR drive
     the value through the real state path (dispatch PLAYER_SCORE) — as S4
     already does deterministically.
  b) Product-side: make the per-frame push diff-aware (only touch the DOM
     when the value changed) so external drives are not clobbered mid-frame;
     this also removes a per-frame textContent write (minor perf win).
