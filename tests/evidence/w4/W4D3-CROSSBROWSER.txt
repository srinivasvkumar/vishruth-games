DETAIL — TEST 3: FPS benchmark @ 120 obstacles (D4 gate: >=60 FPS)
================================================================================
CHROME (chromium-boot, SwiftShader GL) — 15 s window, 901 frames
  mean FPS:      60.0
  median FPS:    59.9
  min FPS:       59.5 (worst single frame)
  p95 frame time: 16.7 ms
  D4 GATE:       MET (60.0 >= 60)
  renderer: draw calls 125→137, triangles 1490→1634, scene groups 124→136

FIREFOX — 15 s window, 899 frames (run 1) / 900 frames (run 2, reproducibility)
  run 1: mean 59.9, median 58.8, min 30.0, p95 17.2 ms
  run 2: mean 59.9, median 60.2, min 29.9, p95 17.2 ms
  D4 GATE:       "NOT MET" (59.9 < 60) — by 0.1 FPS, REPRODUCIBLE across 2 runs
  renderer: draw calls 125→137, triangles 1490→1634 (identical workload to Chrome)

  BROWSER-SPECIFIC INTERPRETATION:
  - Identical scene workload (120 THREE meshes + 120 per-frame JS obstacles +
    120 physics bodies). Chrome's rAF holds a hard 60.0 (vsync-locked). Firefox
    averages 59.9 — 0.1 FPS below the integer gate, with median swinging 58.8→60.2
    between two runs and a single dropped frame (min ~30 = one 2-frame gap) in
    each run. This is the 60-Hz vsync floor: Firefox's rendering pipeline is
    delivering ~59.9 vs ~60.0 of the display's 60 fps cadence. It is NOT a
    perf regression or a 2-frame defect (p95 17.2 ms ≈ 1 frame, not ~33 ms).
  - Classification: MINOR / browser-specific. The D4 gate is an integer ">=60"
    test that trips on a 0.1-FPS rounding difference between two rendering
    engines at the same vsync cadence. Substantive 60-fps performance is met in
    both (p95 frame time ~1 frame, no sustained drops). Flagged for orchestrator
    to decide if the gate should be a tolerance band (e.g. >=59) rather than
    exact 60, given cross-browser vsync variance.

DETAIL — TEST 5: 5-minute memory leak test
================================================================================
Method: 5x play→die→restart cycles (~12 s each, the spawn/destroy + audio +
scene-swap churn the leak check targets) + 240 s steady-state play, sampling
every 15 s. Verdict via least-squares slope on the metric (a sawtooth/bounded
fluctuation has ~zero mean slope; a real leak shows a sustained positive slope).

CHROME — metric: performance.memory.usedJSHeapSize (authoritative JS heap)
  heap: pinned at 9765–9766 KB across ALL 17 samples (no drift at all)
  least-squares slope: 0.00% of mean per 15 s   growth first→last: 0.0%
  verdict: STABLE  →  NO LEAK
  (obstacle array grew 13→161 over the window — see the proxy caveat below;
   the JS heap stayed byte-for-byte flat despite that accumulation)

FIREFOX — metric: obstacleCount proxy (performance.memory is UNAVAILABLE in
Firefox; the spec falls back to a browser-agnostic object-count proxy)
  obstacle count: 3 → 162 (grows, same pattern as Chrome's 13 → 161)
  least-squares slope: +12.04% of mean per 15 s   growth first→last: +5300%
  raw verdict: GROWING/LEAKING
  DOM node count: flat at 139 across the whole window (no DOM leak)

  BROWSER-SPECIFIC INTERPRETATION (false-positive avoidance):
  - The obstacle-count growth is NOT a leak. It is an artifact of the test setup:
    the player is idle at spawn (no input) while obstacles spawn continuously
    ahead (negative z). W4-B.11's reapOffscreenObstacles() only reaps obstacles
    that pass REAP_Z = -250 BEHIND the player — an idle player never advances,
    so spawned obstacles never cross REAP_Z and are not reaped. The count therefore
    grows by the spawn rate, identically in BOTH browsers (Chrome 13→161,
    Firefox 3→162).
  - The DEFINITIVE leak signal is Chrome's real JS heap: byte-flat at 9766 KB
    through the entire 5 restart cycles + 4 min of identical obstacle
    accumulation. If obstacles (or their meshes/audio nodes) leaked, Chrome's
    heap would climb. It did not.
  - Firefox cannot expose the JS heap to JS, so its proxy (obstacle count) cannot
    distinguish "growing-by-design unbounded run" from "leak". The proxy's
    GROWING verdict is a measurement limitation, not evidence of a defect.
  - Cross-browser conclusion: NO MEMORY LEAK. Chrome's authoritative heap is
    flat; Firefox shows the same bounded DOM + the same design-level obstacle
    accumulation, with no signal of unbounded JS growth.

   [KNOWN — carried from W4-A.1]

3. Input latency: Firefox p95 15.0 ms (TARGET MET) vs Chrome p95 16.5 ms
   (0.5 ms over, 1-frame boundary). Firefox marginally better. [NON-ISSUE]

4. Memory visibility: performance.memory (JS heap) exists in Chrome only;
   Firefox must use an object proxy, which cannot see JS-heap growth. This is
   why Firefox's raw memory verdict reads GROWING (proxy artifact) while Chrome
   reads STABLE (authoritative). The authoritative cross-browser signal is
   Chrome's flat heap + both browsers' flat DOM. [MEASUREMENT LIMITATION]

================================================================================
DEFECTS
================================================================================
1. [minor / browser-specific] FPS D4 gate trips on Firefox by 0.1 FPS (59.9 < 60)
   at 120 obstacles. Reproducible. Not a perf regression — p95 frame time is
   ~1 frame in both browsers. Recommend the gate use a tolerance band
   (>=59) to absorb cross-engine vsync variance, OR document that the D4 gate
   is Chrome-anchored and Firefox is "at the 60-fps floor". No product code
   change required.

2. [known / spec defect, carried from W4-A.1] CP3 S2 (#game-score DOM updates
   when setScore is driven) is a frame-timing race between the spec's setScore
   drive and the per-frame HUD push. Deterministic on Chrome, flaky on Firefox.
   Product score functionality is healthy (S1/S4 pass in both). Spec-side fix
   (assert the DOM read inside the same evaluate() that drives setScore, or
   drive + settle a frame) is required to make CP3 evidence trustworthy in
   either browser. No product code change.

3. [measurement limitation] Firefox memory test cannot read JS heap
   (performance.memory undefined). Its obstacle-proxy verdict "GROWING" is a
   false positive caused by the idle-player test setup (unbounded run, obstacles
   never cross REAP_Z to be reaped). Chrome's flat authoritative heap + both
   browsers' flat DOM prove NO LEAK. If a Firefox-native heap check is ever
   required, run under about:memory / DevTools Memory profiling or a CDP-like
   extension, not a pure-JS page.
